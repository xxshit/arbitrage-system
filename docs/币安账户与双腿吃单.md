1. **先准备再开放确认。** 独立执行器预先建立两市场连接及用户成交事件流，准备限流额度、账户版本和必要规则。交易规则/费率/权限缓存须有期限、版本和失效路径；余额、挂单、持仓还须持续对账，不能以“缓存优化”跳过核验。确认提交用通知唤醒、持久队列兜底，避免等待下一秒轮询。数量、价格保护、退出预算及一次授权范围在确认前展示。
2. **用新鲜深度形成可成交报价。** 页面继续 5 秒刷新；执行器另用有序增量盘口，按各市场的序列规则维护，断流、缺口或过期就暂停并重建。合约开空看买盘、现货买入看卖盘；同时检查现货卖出和合约买回的反向深度。按共同步长、手续费可能扣基础币后的净差额、四侧深度、预算及单腿容忍量选择小批数量。确认页显示这批数量的逐档均价，不把买一/卖一当成整批成交价。当前固定深度 10%、50/500 ms 等尚未由真实链路分布校准。
3. **两路就绪后共同放行。** 签名、连接准备、限流/锁等待与请求编码放到放行前；任一路未就绪时零发送。记录真实请求首字节和完整请求体写入时刻、响应时刻、交易所成交时刻；保留每个指标的测量边界。开仓继续使用小批限价 FOK，不扩大确认的价格范围。放行后仍可能发生单路失败，必须转入不确定/敞口处置，不能宣称本机屏障锁住交易所盘口。
4. **两腿独立接收成交证据。** 以用户数据流跟踪成交，按订单号和成交 ID 去重、校验数量/费用；REST 独立并行补查，两条路径分别保存进度，一腿失败不跳过另一腿。设置明确的总时间预算，而非只依赖每次 socket 读取超时。接收超时不等于未成交；未知状态只核对原订单，禁止重发开仓或根据未知数量盲目反向下单。
5. **事先计算能否减掉单腿。** 减仓按最新反向盘口、已核实成交均价与单独确认的退出价格/费用预算计算限价；数量只减少本次净敞口。开仓前若最小交易单位或反向深度使这一批无法在预算内退出，拒绝开仓。开仓后市场仍会变，限价 IOC 不能保证一定退出；剩余量和未知状态必须显式保留、暂停新批次，不能伪报完成或无限追价。每笔仍只执行用户明确确认的一批。

优先修发送测量/双路准备、反向减仓定价和独立对账，再接持续盘口/成交事件流，最后依据测得的链路尾延迟校准门限。验证采用断线重连、单腿拒绝、写出后超时、事件乱序/丢失、反向深度撤单、基础币扣费和进程恢复等确定性短场景，逐项核对“实际发了什么、成交多少、还剩多少”。不靠重复两小时测试掩盖逻辑缺口；也不把模拟撮合当作真实双腿成交成功率。

官方边界：现货 [FOK 定义](https://developers.binance.com/en/docs/products/spot/enums) 只约束单笔订单；两市场各自下单，不能从两个 FOK 推导为跨市场原子成交。[现货盘口维护](https://developers.binance.com/en/docs/products/spot/web-socket-streams) 要求对更新序列缺口重建；[现货用户流](https://developers.binance.com/en/docs/products/spot/user-data-stream) 与 [USDT 合约用户流](https://developers.binance.com/en/docs/products/derivatives-trading-usds-futures/user-data-streams) 可提供成交事件；[合约未知执行状态](https://developers.binance.com/en/docs/products/derivatives-trading-usds-futures/general-info) 要求先核实，不应直接认定失败并重复下单。优化方案基于这些接口边界推导，未声称币安提供双腿同成同撤接口。

## 数量、价格和时间

用户要求两腿数量不能差太远、不能明显先后成交，也不能远离看到的价格。两市场没有统一提交事务：一个市场的 FOK 仅保证该笔订单全成或取消，不能保证另一市场同时成功。因此采用以下约束，而不把“并发”宣称为双腿原子成交：

1. 用现货卖盘和合约买盘的真实深度逐档计算可成交均价，只使用确认限价内可见数量的最多 10%。取两边较薄的深度、预算、单批限额和交易规则共同允许的数量。
2. 现货与合约使用相同基础币数量。两市场步长求公倍步长，按步长向下取整；不把相同 USDT 金额当作相同币数。不同基础币或倍率合约拒绝执行。
3. 同时发出限价 FOK：现货 BUY、永续 SELL。现货最高买价和合约最低卖价固定，发送前只能收紧，不能放宽或改成无价格保护的市价单。
4. 两份盘口的请求年龄最多 1 秒，单次往返最多 400 ms，发起时差最多 100 ms。用户确认最多有效 15 秒；提交前重新核验账户和盘口，持久化订单意图后再取一次盘口，数量变化则两腿都不发。
5. 当前版本先完成两路连接/签名/编码再共同放行，记录本机写入入口及完整写完时刻；两项 50 ms 门限和成交跨度 500 ms 都须有证据。旧版回调没有覆盖自动建连，旧记录不能套用新计时语义。缺失或超限即使数量一致也暂停后续执行；这些事后规则不能撤回已发生的单腿或成交时差。
6. 默认单批 20 USDT，用户可设置 5–1000 USDT，且不得超过总预算。若交易所最小数量/金额要求更高，显示共同最小数量及所需金额，由用户调整，不自动放大订单。BTC 合约的最小数量可能比 50 USDT 名义门槛更严格。

开差校验采用账户实际费率，现货保守计入 standard、special、tax 的 taker+buyer 项，不预先假定 BNB 折扣。真实成交手续费单独核对；若从基础币扣费，现货净数量减少，必须把差额显示出来。最低扣费开差是入场价格边界，未包含未来平仓费、资金费、价格变化，也不承诺收益。界面的单腿 USDT 数值是按确认价格估算的名义敞口，绝非最大损失保证。

## 异常及恢复

- 订单意图先写数据库，再发送订单。两腿使用从唯一意图生成的固定 client order ID；同一确认重复点击不会新增意图或补发。
- 超时、503、响应损坏、重复 ID 等状态不明确时只按原订单号查询。未知订单不会被当作“没成交”，不会重下，也不能通过接管按钮解锁。
- 按订单号读取成交明细，核对订单、方向、吃单标志、价格限额、逐笔数量和手续费。明细不全（包括超过单页 1000 条）暂停，不用估算手续费冒充准确对冲。
- 可选差额处置为“暂停并由本人处理”或“限价减掉本次多余敞口”。后者最多发送一次 IOC，只减少本意图产生的多余一腿，受独立确认的退出价差和最新反向盘口限制；费用另列，不买入缺失腿追平，不向上取整成最小订单。仍有差额/零碎数量则保留并锁定账户。
- 单向模式合约减仓使用 reduceOnly；双向模式使用 SHORT 的 BUY，不发送该模式不支持的 reduceOnly 参数。已有该合约仓位或任一市场挂单时首版拒绝开始，避免混入其他仓位。
- 进程恢复仅查询已持久化的订单号；不重发开仓单，也不自动重试减仓。只有两腿及减仓都已核清终态，才允许用户明确接管已显示的差额。接管不表示已经平仓或完全对冲。
- 已配对后仍不自动继续后续批次。当前首版不支持叠加同合约已有仓位。

## 账户与运行隔离

仅接受开启读取、限制服务器 IP、关闭提现/内部转账/通用转账的专用 Key。下单核验另外要求现货和合约交易权限；不自动修改币安权限、杠杆或持仓模式。仅支持普通单资产 USDT 合约账户，杠杆须与币安已有 1–10 倍设置相同。

Key/Secret 只经 HTTPS 密码表单提交，保存后不回显，不写浏览器持久存储、URL 或诊断日志。AES-GCM 使用独立 32 字节服务器密钥，以站内 user ID 绑定密文；文件必须为所属服务用户持有的 600 普通文件。一个币安 UID 不能绑定多个站内用户。

新增三表：`binance_account_link`、`binance_hedge_intent`、`binance_executor_health`。导入模块不建表、不启动线程；备份后显式安装表。数据库事务均在网络请求前结束。418/429 冷却落库，跨网页请求和执行器保持，不能靠重新创建客户端绕过。

网站只验证、展示和排队；`python -m binance_hedge.worker --serve` 在独立进程执行，私有 flock 保证本机单执行器。服务模板 `deploy/arbitrage-binance.service` 默认 `BINANCE_EXECUTION_ENABLED=0`。真实下单要求网站开关、执行器开关和新鲜心跳同时满足，且每笔仍需用户确认。模板交付不代表已运行或获准真实交易。
