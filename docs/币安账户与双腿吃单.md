# 币安账户与双腿吃单

## 当前范围（2026-11-07）

首版实现管理员接入专用 HMAC API Key、手动读取现货余额/合约持仓、Binance 现货买入与同币 USDT 永续开空的实盘口核验，以及独立执行器。部署时真实下单开关保持关闭；没有提交真实订单，也没有用真实账户证明双腿成交效果。其他交易所、期多期空、加仓、自动连续分批及平仓管理不在本版执行范围内。

全站行情刷新仍为 5 秒。账户余额由本人手动刷新；每 5 秒读取的执行状态来自本站数据库，不等同于每 5 秒请求币安私有账户。每次确认只授权下面实际显示的一批，不自动执行总预算余量。

## 数量、价格和时间

用户要求两腿数量不能差太远、不能明显先后成交，也不能远离看到的价格。两市场没有统一提交事务：一个市场的 FOK 仅保证该笔订单全成或取消，不能保证另一市场同时成功。因此采用以下约束，而不把“并发”宣称为双腿原子成交：

1. 用现货卖盘和合约买盘的真实深度逐档计算可成交均价，只使用确认限价内可见数量的最多 10%。取两边较薄的深度、预算、单批限额和交易规则共同允许的数量。
2. 现货与合约使用相同基础币数量。两市场步长求公倍步长，按步长向下取整；不把相同 USDT 金额当作相同币数。不同基础币或倍率合约拒绝执行。
3. 同时发出限价 FOK：现货 BUY、永续 SELL。现货最高买价和合约最低卖价固定，发送前只能收紧，不能放宽或改成无价格保护的市价单。
4. 两份盘口的请求年龄最多 1 秒，单次往返最多 400 ms，发起时差最多 100 ms。用户确认最多有效 15 秒；提交前重新核验账户和盘口，持久化订单意图后再取一次盘口，数量变化则两腿都不发。
5. 最后一次本机发送门在连接锁内、签名和限流检查之后，紧邻网络写入；若第二腿本机发送已落后超过 50 ms，不再发送迟到腿，并对第一腿真实结果对账。网络与交易所仍可能造成先后到达、单腿成交。全部成交时间跨度超过 500 ms，或缺少时间证据，即使数量一致也暂停后续执行。
6. 默认单批 20 USDT，用户可设置 5–1000 USDT，且不得超过总预算。若交易所最小数量/金额要求更高，显示共同最小数量及所需金额，由用户调整，不自动放大订单。BTC 合约的最小数量可能比 50 USDT 名义门槛更严格。

开差校验采用账户实际费率，现货保守计入 standard、special、tax 的 taker+buyer 项，不预先假定 BNB 折扣。真实成交手续费单独核对；若从基础币扣费，现货净数量减少，必须把差额显示出来。最低扣费开差是入场价格边界，未包含未来平仓费、资金费、价格变化，也不承诺收益。界面的单腿 USDT 数值是按确认价格估算的名义敞口，绝非最大损失保证。

## 异常及恢复

- 订单意图先写数据库，再发送订单。两腿使用从唯一意图生成的固定 client order ID；同一确认重复点击不会新增意图或补发。
- 超时、503、响应损坏、重复 ID 等状态不明确时只按原订单号查询。未知订单不会被当作“没成交”，不会重下，也不能通过接管按钮解锁。
- 按订单号读取成交明细，核对订单、方向、吃单标志、价格限额、逐笔数量和手续费。明细不全（包括超过单页 1000 条）暂停，不用估算手续费冒充准确对冲。
- 可选差额处置为“暂停并由本人处理”或“限价减掉本次多余敞口”。后者最多发送一次 IOC，只减少本意图产生的多余一腿，受原确认价格和滑点限制；不买入缺失腿追平，不向上取整成最小订单。仍有差额/零碎数量则保留并锁定账户。
- 单向模式合约减仓使用 reduceOnly；双向模式使用 SHORT 的 BUY，不发送该模式不支持的 reduceOnly 参数。已有该合约仓位或任一市场挂单时首版拒绝开始，避免混入其他仓位。
- 进程恢复仅查询已持久化的订单号；不重发开仓单，也不自动重试减仓。只有两腿及减仓都已核清终态，才允许用户明确接管已显示的差额。接管不表示已经平仓或完全对冲。
- 已配对后仍不自动继续后续批次。当前首版不支持叠加同合约已有仓位。

## 账户与运行隔离

仅接受开启读取、限制服务器 IP、关闭提现/内部转账/通用转账的专用 Key。下单核验另外要求现货和合约交易权限；不自动修改币安权限、杠杆或持仓模式。仅支持普通单资产 USDT 合约账户，杠杆须与币安已有 1–10 倍设置相同。

Key/Secret 只经 HTTPS 密码表单提交，保存后不回显，不写浏览器持久存储、URL 或诊断日志。AES-GCM 使用独立 32 字节服务器密钥，以站内 user ID 绑定密文；文件必须为所属服务用户持有的 600 普通文件。一个币安 UID 不能绑定多个站内用户。

新增三表：`binance_account_link`、`binance_hedge_intent`、`binance_executor_health`。导入模块不建表、不启动线程；备份后显式安装表。数据库事务均在网络请求前结束。418/429 冷却落库，跨网页请求和执行器保持，不能靠重新创建客户端绕过。

网站只验证、展示和排队；`python -m binance_hedge.worker --serve` 在独立进程执行，私有 flock 保证本机单执行器。服务模板 `deploy/arbitrage-binance.service` 默认 `BINANCE_EXECUTION_ENABLED=0`。真实下单要求网站开关、执行器开关和新鲜心跳同时满足，且每笔仍需用户确认。模板交付不代表已运行或获准真实交易。

## 备份、部署与证据边界

新增独立 `.binance_api_encryption.key` 不进入 Git；定期 SQL 备份同时保存私有的按 SHA 命名恢复密钥，并在 SQL 旁记录配对指纹。密钥不得进入只读 SQL 下载导出。恢复后先保持执行关闭、对账存量意图，不恢复数据库后自动重下。

本地 `app.py` 仍含未验收的内存候选。此次生产候选从已部署 `89b8002` 组装，只添加蓝图注册与仓位说明；其他内存改动不随本版上线。部署使用新目录、新热备、新保护摘要和源码清单。原 51 张业务表、原索引、账户/仓位/停盯盘/规则及游戏/MySQL 身份分别核验；仅新增上述三表。

本轮合成回归覆盖数量/精度/费用、变薄盘口、迟到发送、超时未知、重复确认、单腿/非整批回报、一次限价减仓、恢复只查询、权限/CSRF、密钥不回显和界面过期。桌面、390/320 宽度的只读合成页面已检查。公开 BTC 交易规则也与实际 API 对照过；这些均不是实盘成交验证，也不是生产内存验收。原内存持续增长仍待归因，不以本次正常功能重载后的低 RSS 宣称修复。
