# 性能诊断与自我修复

## 2026-10-18 机会看板刷新不符合5秒目标（本地完成，待部署）

- 根因是多层周期叠加：浏览器请求完成后再等5秒；看板三币三所价格另有15秒缓存；同一个`/api/dashboard`请求还同步等待大盘多接口分析、涨势评分和市值双源计算。后两项过期重算时会阻塞行情展示，原顶部时间却只代表浏览器请求完成。
- 看板改为四条独立后台通道：真实三所最新成交价按`spot_market_refresh`目标节拍采集（当前5秒），BTC/ETH/SOL结构约30秒，涨势评分和持仓市值榜各约5分钟。保持原成交价口径和策略公式，不把盘口中间价混成最新成交价；不改变Lark、自动交易或数据库结构。
- HTTP只读取已发布内存缓存；浏览器与响应均禁止缓存。行情请求并行、单次网络超时1.5秒；不依赖每15秒落库的行情来冒充5秒更新。后台按单轮开始时间扣除工作耗时；分析任务强制执行到期轮次，避免TTL临界误差跳过整轮。
- 浏览器看板改为请求开始到开始的5秒目标，不叠加响应耗时；正在请求时不重叠，手动连点合并，10秒未返回则中止并允许下一轮重试。其他页面原有完成后计时方式保留。
- 顶部与价格卡显示真实行情采集时间，结构另有独立时间。每行缺所标明，整币失败保留原价格和原时间；默认超过15秒标延迟，阈值随配置周期调整；过期价差不作为当前机会显示。仅余一家交易所时保留价格而不生成跨所收益。

## 2026-07-28 卡顿原因

1. 旧 Flask 进程未真正退出。Windows 虚拟环境存在启动器与实际 Python 进程，按端口结束进程时没有完整替换，导致新代码未加载。
2. 页面无论当前位于哪个栏目，都会同时刷新看板、现多期空、期多期空、套利思维与趋势验证，形成隐藏页面请求堆积。
3. `futures_price_history` 已超过 118 万行，盯盘管理曾把一个币时间范围内的全部价格记录加载到 Python 才计算高低点。
4. 历史资费统计曾一次读取约 8 万条 ORM 记录；并发首轮请求还会重复执行相同查询。
5. 行情每 5 秒采集时，同时把大量最新快照写入 MySQL，并在同一价格桶内反复清理历史表，使数据库持续繁忙。

## 已实施修复

- 页面只刷新当前显示的栏目；全局报警仍保持 5 秒刷新。
- 历史资费改为 MySQL 条件聚合，并增加 60 秒缓存和并发防重锁。
- 盯盘高低点改为数据库聚合查询，最近推送改为批量读取。
- 实时行情仍每 5 秒采集并进入内存快照；MySQL 最新行情按 15 秒落库，报警事件仍即时落库。
- 5 分钟价格历史同一时间桶只写一次，不再每 5 秒重复扫描百万行历史表。
- 现多期空与期多期空后台任务错峰运行；静态指数成分检查由 5 秒改为 5 分钟。
- 后台单轮超过 5 秒时保留最小休息时间，避免失败或网络变慢后形成无间隔死循环。

## 修复后基准

- 后台现多期空完整处理：约 2.9 秒，低于 5 秒目标周期。
- 现多期空缓存读取：约 0.64 秒。
- 期多期空缓存读取：约 0.07 秒。
- 报警中心：约 0.32 秒。
- 盯盘管理：约 0.07 秒。

## 后续自检原则

- 每次重启后必须检查 Python 进程启动时间，确认旧进程已消失。
- 使用 `/api/refresh-diagnostics` 检查网络、报警计算、快照写入和历史写入各阶段耗时。
- 若后台总耗时再次超过 5 秒，优先排查交易所网络、MySQL 活跃查询、历史表规模和重复进程。
- 固定历史资料采用低频落库；实时价格采用高频内存快照加周期性 MySQL 持久化。
