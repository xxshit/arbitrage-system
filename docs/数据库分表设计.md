# 数据库分表设计

目标：交易系统里的数据不能混在一起。实时行情、历史行情、资费、报警、日报、思路复盘、交易所元数据都要按功能分表，方便查询、维护、备份和以后迁移云服务器。

## 1. 实时行情快照表

这类表只保存“最新状态”，页面排序、分页、筛选都优先读这些表，不要因为用户点击页面就重新请求交易所。

| 表名 | 功能 |
| --- | --- |
| `latest_market_snapshot` | 现多期空：现货交易所对 Binance 合约的最新价差、基差、资费、成交量、持仓量 |
| `latest_dual_futures_snapshot` | 期多期空：BY/OK/BN 合约路径的最新开差、平差、基差、资费差、持仓量、交易量 |

## 2. 历史行情与资费表

这类表用于趋势灯、涨跌幅、详情弹窗、日报趋势和历史资费统计。

| 表名 | 功能 |
| --- | --- |
| `futures_price_history` | Binance 合约价格历史采样 |
| `dual_futures_price_history` | BY/OK/BN 合约价格历史采样 |
| `funding_rate_record` | Binance 历史资金费率，滚动保留最近 30 天 |

规则：历史资费是固定事实，写入后优先复用；超过保留周期再清理，避免 MySQL 越来越大。

## 3. 报警与基差打开表

这类表用于报警中心、全局 TIPS、基差打开次数、最大值和误报警复查。

| 表名 | 功能 |
| --- | --- |
| `alert_event` | 报警事件，包括开差、基差、速变等 |
| `basis_tracking` | 基差第一次打开、方向、最近最大值、最大值时间 |
| `basis_expansion_log` | 基差每扩大 0.2% 的打开记录 |

规则：同一币种同一路径的报警不能无脑重复；只有第一次触发，或绝对值比上一轮报警扩大至少 0.2%，才刷新报警。

## 4. 交易所低频元数据表

这类数据通常不频繁变化，拉到后存 MySQL，以后页面直接读库。

| 表名 | 功能 |
| --- | --- |
| `index_component_snapshot` | BN/BY/OK 合约指数成分 |
| `transfer_network_snapshot` | 现货交易所充提链与充提状态 |
| `listing_state` | 上下架状态基线 |
| `listing_event` | 上架、下架、公告事件，包含公告时间和具体生效时间 |

## 5. 日报、趋势与推送状态表

这类表用于每天固定时间的趋势扫描、Lark 推送去重和任务健康检查。

| 表名 | 功能 |
| --- | --- |
| `daily_horn_signal` | 每日犄型走势候选，分 30M 和 4H |
| `lark_push_state` | Lark 推送去重，避免重复发同一个信号 |
| `automation_status` | 自动任务最近开始、成功、失败时间 |

## 6. 策略与后续要新增的思路复盘表

已有：

| 表名 | 功能 |
| --- | --- |
| `strategy` | 基础策略配置 |

下一步建议新增，不要再把思路分析写死在代码里：

| 建议表名 | 功能 |
| --- | --- |
| `trade_thesis` | 单个币的交易思路：币种、方向、入场价、入场时间、用户观点、Codex 观点、当前状态 |
| `trade_thesis_snapshot` | 盯盘快照：价格、资费、基差、持仓、CVD、量能、判断 |
| `trade_thesis_review` | 复盘：哪里对、哪里错、止盈止损是否合理、后续修正 |

这样 AKE、T、US 这类分析就会变成可追踪、可统计胜率、可复盘的数据，而不是零散文本。

## 当前结论

当前 MySQL 已经不是“所有数据混在一张表里”，核心模块已经分表。下一步最需要拆出来的是“思路分析/盯盘/复盘”三张表，因为这是后期你和我共同进化交易思维的核心资产。

## 7. 账号安全与聊天表

| 表名 | 功能 |
| --- | --- |
| `user_account` | 账号、不可逆密码哈希、角色、登录会话摘要、最近密码更新时间 |
| `account_security_event` | 管理员密码重置审计，只记操作者、目标、方式与时间，不记任何密码 |

| 表名 | 功能 |
| --- | --- |
| `chat_message` | 账号之间的一对一消息；正文以AES-256-GCM密文保存，发送者、接收者、引用消息ID和时间保留为查询元数据 |
| `chat_attachment` | 图片消息的附件元数据与AES-256-GCM加密二进制；独立于文字表并通过登录鉴权接口解密读取 |
| `chat_view_state` | 每个账号自己的清空游标和已读游标 |
| `chat_message_preference` | 每个账号对单条消息的个人删除、个人置顶状态；同一消息双方状态互不影响 |

规则：个人点击清空时不得立即删除 `chat_message`，只推进该账号自己的 `cleared_through_id`；单条删除同样只写入 `chat_message_preference.hidden_at`。因此两种操作都不会改变对方的聊天历史。全局留存上限为 30 天，超过后物理删除双方原始消息、附件及对应个人偏好；图片跟随 MySQL 一起备份和恢复。

账号表 `user_account.chat_nav_hidden` 只保存当前账号是否隐藏左侧“协作记录”入口。该偏好按账号隔离，管理员修改自己的状态不会改变其他账号；它不是聊天内容，也不写入 `runtime_rule` 全局规则表。

聊天表的`encryption_version`用于区分历史明文与当前密文并保证迁移幂等。加密密钥只能保存在项目外的私密密钥文件或私密环境配置中，不能进入MySQL、Git、文档或日志；拥有完整服务器root权限并取得该密钥的人仍可解密，这不是端到端加密。

密码安全规则：数据库只能保存安全哈希，不能保存可还原或可查看的明文密码。忘记密码通过管理员重置解决；重置会使目标账号已有会话立即失效，并留下不含密码内容的审计事件。

## 8. 多周期趋势验证表

| 表名 | 功能 |
| --- | --- |
| `trend_horizon_validation` | 保存同一时点的短线、中线、长线独立假设、虚拟止盈止损、验证窗口、MFE/MAE、第一触发和复盘结论 |
| `trend_horizon_event` | 保存止盈、软警戒、硬止损、接近目标后反转、阶段复核和到期复盘等路径事件 |

规则：三个周期用同一个`batch_key`关联，但各自独立判断；触发止盈或止损后不删除、不覆盖，继续观察到周期结束，以便识别扫损后反转和目标过远。行情K线仍复用`trade_validation_candle`，不重复存整套K线。
## 趋势验证K线缓存

记录时间：2026-07-21

新增表：`trade_validation_candle`

用途：专门服务“趋势验证”页面，不再每次画图时临时从交易所拉一大段K线，也不再用通用价格快照模拟K线。

字段规划：

- `symbol`：币种，例如 `ACE/USDT`。
- `interval`：K线周期，当前固定为 `5m`。
- `bucket_at`：该根K线开始时间戳，按5分钟对齐。
- `open/high/low/close`：真实OHLC价格。
- `volume`：成交量。
- `quote_volume`：USDT成交额。
- `captured_at`：写入时间。

唯一键：`symbol + interval + bucket_at`，避免重复写入同一根K线。

缓存规则：

- MySQL保留最近7天趋势验证K线。
- 页面默认显示最近3天K线，方便横向滑动查看昨天和更早的买入/卖出点。
- 每次刷新先检查库里的最新K线；如果中间没有缺口，只向交易所补最新缺失K线；已有K线直接从MySQL读取。
- 前端刷新时保留旧图和横向滚动位置，新数据回来后再替换，避免页面先空白。
