# 数据库备份与灾难恢复

## 保护目标

GitHub 只负责保存代码、数据库结构和备份程序，不保存真实数据库文件、`.env`、密码、SSH 私钥。真实 MySQL 数据采用独立的三层保护：

1. 云服务器每 6 小时生成一次热备份，保留 14 天；每天另留一份，保留 90 天。
2. 本机每天 09:30 通过 SSH 拉回最新备份，校验 SHA-256 后保留 180 天；电脑关机错过任务时，下次开机后补跑。
3. 后续接入对象存储（阿里云 OSS、AWS S3 或 Backblaze B2）作为异地副本，开启服务端加密、版本控制和生命周期。异地存储凭据只写在云服务器私密环境文件中，不能提交 Git。

云服务器和本机同时损坏的概率远低于单点损坏；接入对象存储后，服务器被整个清除也能恢复到最近一次异地备份。

## 当前脚本

- `scripts/backup_mysql.sh`：云端原子热备份、压缩、校验和分层清理。
- `scripts/run_mysql_backup_loop.sh`：由 PM2 常驻，每 6 小时执行一次备份。
- `scripts/pull_cloud_mysql_backup.ps1`：本机触发云端备份、下载并校验。
- `scripts/install_local_backup_task.ps1`：安装 Windows 每日拉取任务。

本机服务器地址、SSH端口和私钥路径写在被Git忽略的`cloud-backup.local.json`中。首次配置时复制`cloud-backup.example.json`，再填写真实信息；不要把本机私密配置加入仓库。

真实备份默认位于：

- 云端：`/var/backups/arbitrage-hub/mysql/`
- 本机：`F:\套利系统\backups\cloud-mysql\`

两个目录都不进入 Git。

## 恢复顺序

1. 从 GitHub 重新拉取项目代码。
2. 安装 Python、MySQL/MariaDB 和依赖，创建空数据库。
3. 取最新且 SHA-256 校验通过的 `.sql.gz` 备份。
4. 恢复前停止网站后台采集进程，避免恢复过程中产生新写入。
5. 在新服务器执行：

   ```bash
   gzip -t arbitrage_hub-YYYYMMDD-HHMMSS.sql.gz
   gunzip -c arbitrage_hub-YYYYMMDD-HHMMSS.sql.gz | mariadb
   ```

6. 补回服务器自己的 `.env`，启动网站并核对账户、行情快照、资费历史、报警、思路分析和趋势验证。
7. 核对无误后再恢复采集和推送任务。

恢复属于覆盖性操作，执行前必须先给当前数据库再做一份备份，且不能直接对仍在写入的生产库操作。

## 异地对象存储建议

数据库备份不能放进普通 Git 仓库：它会放大仓库体积，Git 历史无法真正删除敏感数据，还可能暴露账户记录。推荐新建一个私有 OSS/S3 存储桶，只允许备份账号写入，开启：

- 服务端加密；
- 版本控制；
- 禁止公共访问；
- 90 至 180 天生命周期；
- 上传失败告警。

取得存储桶、地区和最小权限密钥后，再把异地上传接到现有备份脚本。密钥只放服务器私密配置，不写在代码或文档中。
