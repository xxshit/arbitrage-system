## 2026-10-20：图表历史独立恢复边界

- 新增现多期空开差／基差历史位于应用`instance/spread-history/YYYY-MM-DD.sqlite3`，只含公开行情采样。它不在MySQL备份中，不能声称恢复SQL就恢复了这部分历史；账号、仓位、公告、报警、资费等既有完整热备不变。
- 每小时通过SQLite online backup生成`instance/spread-history/checkpoints/同日期.sqlite3`，按日复用恢复副本，避免每6小时再复制全段15天数据。原分片和副本都保留最近15天及边界日，物理最多16日期；只清理严格日期命名的本功能文件，不碰其他数据库或配置。
- 普通重启直接续写原分片。同分钟按真实时刻合并极值，不覆盖先前极值；尚未持久化的约30秒观测可能丢失。恢复某损坏分片时，先停网站、另存原分片及WAL/SHM，再核验对应checkpoint完整性并恢复同名路径，修正arbhub所有权后启动；checkpoint可能落后故障约1小时，不补画损失区间。
- 迁移时必须额外复制这些分片／checkpoints（停写后复制或用SQLite备份接口），随MySQL和私密密钥之外单独核对。当前checkpoint和原文件同盘，**不防整机／磁盘丢失，尚未接入异地存储**。写入／生成副本在可用空间低于1GiB时失败并保留有界重试，不以耗尽业务数据库磁盘换取曲线完整。

## 保护目标

GitHub 只负责保存代码、数据库结构和备份程序，不保存真实数据库文件、`.env`、密码、SSH 私钥。真实 MySQL 数据采用独立的三层保护：

1. 云服务器每 6 小时生成一次热备份，保留 14 天；每天另留一份，保留 90 天。
2. 本机每天 09:30 通过 SSH 拉回最新备份，校验 SHA-256 后保留 180 天；电脑关机错过任务时，下次开机后补跑。
3. 后续接入对象存储（阿里云 OSS、AWS S3 或 Backblaze B2）作为异地副本，开启服务端加密、版本控制和生命周期。异地存储凭据只写在云服务器私密环境文件中，不能提交 Git。

聊天正文和图片从2026-08-03起以应用层密文进入MySQL。数据库备份只包含密文，必须同时保留与该数据库匹配的聊天加密密钥；缺少密钥时，行情、账号等数据仍可恢复，但聊天文字和图片无法解密。

云服务器和本机同时损坏的概率远低于单点损坏；接入对象存储后，服务器被整个清除也能恢复到最近一次异地备份。

## 当前脚本

- `scripts/backup_mysql.sh`：云端原子热备份、压缩、校验和分层清理。
- `scripts/run_mysql_backup_loop.sh`：由 PM2 常驻，每 6 小时执行一次备份。
- `scripts/pull_cloud_mysql_backup.ps1`：本机触发云端备份、下载并校验。
- `scripts/install_local_backup_task.ps1`：安装 Windows 每日拉取任务。
- `scripts/run_cloud_backup_hidden.vbs`：通过无窗口的 `wscript.exe` 执行Windows每日拉取，正常输出和错误统一写入 `logs/cloud-backup-task.log`，避免Windows Terminal每天弹出。
- `scripts/sync_cloud_to_local.ps1`：先备份本地 MySQL，再把已校验的云端备份和匹配聊天密钥恢复到本机。
- `scripts/start_workstation.ps1`：换电脑开始工作时先做 Git 仅快进更新，再执行云库到本地的单向同步。
- `scripts/refresh_backup_export.sh`：云端每次热备成功后，将最新SQL和SHA-256发布为只读、不可变版本；不发布聊天恢复密钥。
- `scripts/pull_cloud_backup_macos.sh`：Mac通过独立只读SFTP账号下载同一版本的SQL与SHA-256，完成校验；不能触发备份或恢复数据库。

本机服务器地址、SSH端口和私钥路径写在被Git忽略的`cloud-backup.local.json`中。首次配置时复制`cloud-backup.example.json`，再填写真实信息；不要把本机私密配置加入仓库。

真实备份默认位于：

- 云端：`/var/backups/arbitrage-hub/mysql/`
- 本机：`F:\套利系统\backups\cloud-mysql\`

两个目录都不进入 Git。

聊天密钥采用独立备份：云端位于`/var/backups/arbitrage-hub/secrets/`，本机拉回到`backups/cloud-secrets/`，两处都不进入Git。备份脚本在密钥缺失时拒绝生成新的SQL备份，避免得到表面成功、实际无法恢复聊天的备份。该密钥属于高敏感恢复材料，不得粘贴到聊天、文档或代码仓库；还应由用户另存一份到可信离线介质或密码管理器。

## Mac只读下载通道

- Mac使用第三把独立密钥 `~/.ssh/arbitrage_backup_mac` 和服务器账号 `arbbackup`，不复用网页隧道或部署密钥。
- `arbbackup` 密码锁定，并被SSH `ChrootDirectory` 限制在 `/srv/arbitrage-backup-export`；强制使用 `internal-sftp -R`，不能打开终端、执行命令、上传、改名、删除、端口转发或读取服务器其他目录。
- 导出目录按备份时间建立不可变版本；`LATEST` 只保存当前版本号。Mac先读取版本号，再从同一版本目录下载数据库和数据库校验文件，避免热备切换时混用不同版本。
- 下载后运行 `bash scripts/pull_cloud_backup_macos.sh`。文件只进入Git忽略的 `backups/cloud-mysql` 并在本机重新校验；该脚本不包含数据库恢复动作。
- 按用户授权，本通道明确不发布聊天恢复密钥。数据库中的聊天正文仍为密文，因此这份副本可恢复行情、账号、盯盘和策略数据，但不能单独恢复可读聊天内容。
- SQL备份仍包含账号哈希和业务运行数据，Mac私钥属于敏感凭据；丢失设备时应立即从服务器撤销对应公钥。

## 恢复顺序

1. 从 GitHub 重新拉取项目代码。
2. 安装 Python、MySQL/MariaDB 和依赖，创建空数据库。
3. 取最新且 SHA-256 校验通过的 `.sql.gz` 备份。
4. 恢复前停止网站后台采集进程，避免恢复过程中产生新写入。
5. 在新服务器执行：

   ```bash
   gzip -t arbitrage_hub-YYYYMMDD-HHMMSS.sql.gz
   gunzip -c arbitrage_hub-YYYYMMDD-HHMMSS.sql.gz | mariadb
   ```

6. 将匹配的`chat-encryption.key`恢复到项目根目录并设置仅应用账号可读，再补回服务器自己的`.env`；密钥必须在首次启动网站前恢复，否则不能读取聊天密文。
7. 启动网站并核对账户、聊天文字与图片、行情快照、资费历史、报警、思路分析和趋势验证。
8. 核对无误后再恢复采集和推送任务。

恢复属于覆盖性操作，执行前必须先给当前数据库再做一份备份，且不能直接对仍在写入的生产库操作。

本地开发副本的标准同步方向固定为“云端生产库到本地”。`sync_cloud_to_local.ps1` 会把覆盖前的本地库保存到 `backups/local-mysql/`，并把旧聊天密钥保存到 `backups/local-secrets/`；这些目录均被 Git 忽略。该脚本不提供本地库自动回写云端的能力，防止旧电脑误覆盖仍在运行的生产数据。

## 异地对象存储建议

数据库备份不能放进普通 Git 仓库：它会放大仓库体积，Git 历史无法真正删除敏感数据，还可能暴露账户记录。推荐新建一个私有 OSS/S3 存储桶，只允许备份账号写入，开启：

- 服务端加密；
- 版本控制；
- 禁止公共访问；
- 90 至 180 天生命周期；
- 上传失败告警。

取得存储桶、地区和最小权限密钥后，再把异地上传接到现有备份脚本。密钥只放服务器私密配置，不写在代码或文档中。
