# 数据库容量治理（2026-10-21）

## 原因和授权

北京时间04:07左右只读核查：约99GiB根分区的普通应用可用空间为0，inode仅3%。游戏旧发布目录约45GiB；MySQL binlog约38.95GiB／426文件，保留30天，10月19日约16.4GiB。套利业务表约632MiB，网站目录约207MiB，独立曲线约132MiB，不是15天曲线占满磁盘。

抽样已关闭的`binlog.000464`，行事件字节约64.1%来自`alert_pulse`、12.8%来自`funding_alert_state`，行情快照两表合计约15.6%。脉冲尾部在每次新报价后更新整段JSON、资金费状态每15秒连同时间戳整体更新，再由ROW/FULL日志保留前后镜像，造成写放大。磁盘不足已出现真实写入错误与MySQL临时表空间不足，进程active不等于业务写入正常。

用户授权：先核验备份，安全清理数据库日志，修复重复写入／保留策略，合并数字评分版本测试部署。不动游戏目录、账户、仓位与行情历史，不推公开仓库。用户随后明确本机空间有限：按小批归档／校验／清理云端／立即删除本机临时副本执行，不长期保存日志副本。

- 未发现已注册副本、复制通道、binlog dump连接或运维配置中的复制／日志消费链路；未来增加外部／离线副本后，必须先重新评估48小时策略，不能只依赖在线连接检查。
- 明确初始清理边界`binlog.000125`，共85份旧文件`000040`至`000124`，原始5,919,489,216字节。每批不超过512MiB原始日志，压缩传到Git忽略／0700本机目录，逐成员SHA-256匹配后用`PURGE BINARY LOGS TO`清理，确认下一文件仍在后删除本机这一批压缩包和清单。
- 首次PURGE因磁盘满写入持锁而超时。仅临时将ext4保留块1097626改为966554（释放512MiB），让MySQL执行已校验首批清理；退出保护随后恢复原1097626，未改变最终保留策略，不手工删除／截断binlog或业务表，不重启游戏或MySQL。
- 已清理旧日志的本机副本按用户要求不长期保留；不能承诺恢复这些旧的逐事务时间点。完整SQL备份继续保留：六小时份14天、每日份90天。独立SQLite曲线／盘口／打开摘要不在MySQL备份里，仍需单独online backup。
- 最终日志策略：MySQL 8 `binlog_expire_logs_seconds=172800`（48小时），`binlog_expire_logs_auto_purge=ON`，通过SET PERSIST重启后保留。部署前使用`configure_mysql_log_retention.sh --check/--apply`核验8小时内完整备份、密钥及复制依赖。默认check只读，不关闭binlog，不变更ROW/FULL，不缩短业务表和完整备份保留期。

官方依据：[MySQL安全PURGE步骤](https://dev.mysql.com/doc/refman/8.0/en/purge-binary-logs.html)、[binlog过期规则](https://dev.mysql.com/doc/refman/8.0/en/replication-options-binary-log.html)、[tune2fs保留块含义](https://man7.org/linux/man-pages/man8/tune2fs.8.html)。

## 应用修复

- 实时检测仍处理每个有效公开报价；普通行情页面5秒、美股15秒、行情快照原15秒落库与原历史采样均不改变。
- `AlertStreamHub`只合并普通脉冲尾部更新，至多15秒写一个最新检查点；新ID、状态／提醒版本变化、终止／缺口／隔离立即入队落库，累计峰值相对已提交峰值至少0.20个百分点也立即写。峰值和范围仍在内存逐样本累计，回落／再次启动不被节流吞掉。
- 写入成功后才推进有界20,000条轻量水位；事务失败重试不消耗事件，写入期间的新版本留队，轮询公平性保持。异常退出可能丢失最多15秒尚未提交的普通末次更新；重大状态按既有写线程立即处理，但不能宣称绝无宕机丢失。
- `funding_alert_state`普通费率／时间戳至多60秒检查点；资费触顶／离顶、周期变化、待核验结算、确认和去重状态变化立即事务提交。至多2,000合约的原子内存缓存向页面提供实时值，事务失败不发布未提交状态，冷启动从原库恢复。原历史资费逐笔记录和累计不改。
- 不降低报警门槛、不新增声音或Lark范围，不丢弃原始事件，不重写既有行情历史，不改账号／交易权限。
