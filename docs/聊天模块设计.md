# 聊天模块设计

记录时间：2026-08-01（2026-08-04 将滚动留存改为 7 天）

## 目标

在 ArbiScope 登录账号之间提供一对一聊天，并满足“任意一方清空自己的聊天记录，不影响对方”的要求。聊天数据独立分表，不能与账号、行情、报警或盯盘表混用。

## 数据表

| 表名 | 作用 |
| --- | --- |
| `chat_message` | 保存发送者、接收者、消息正文、引用关系、撤回状态、发送时间与逐条已读时间。消息是双方共享的原始事实。 |
| `chat_attachment` | 保存图片消息的所属消息、原文件名、可信 MIME 类型、大小、图片二进制和创建时间。 |
| `chat_view_state` | 保存每个账号针对每个联系人的可见游标、已读游标。清空只更新当前账号自己的游标。 |
| `chat_contact_remark` | 保存当前账号为某位联系人设置的私人备注；备注按查看者与联系人独立存储，并使用聊天密钥加密。 |
| `chat_message_preference` | 保存当前账号对某一条消息的个人删除和个人置顶状态；不改变对方看到的消息。 |

## 独立清空语义

1. 甲和乙之间的原始消息仍保存在 `chat_message`。
2. 甲点击“清空我的记录”后，只把甲对应乙的 `cleared_through_id` 更新到当前最后一条消息。
3. 甲再次打开会话时，只读取该游标之后的新消息。
4. 乙的 `chat_view_state` 不发生改变，因此乙仍能看到原历史。
5. 清空后双方发送的新消息对甲、乙都正常显示。

这不是物理删除，也不是端到端加密。聊天正文和图片现已使用应用层AES-256-GCM加密：只查看MySQL或SQL备份无法直接看到内容；网站服务器读取密钥后为有权限的会话参与者解密。拥有完整服务器root权限并同时取得密钥的人仍可解密。

## 接口与前端

- 联系人接口返回其他有效账号、最近消息、在线提示和未读数。
- 消息接口只能读取当前账号与目标账号之间的双向消息。
- 发送和清空操作必须携带当前登录会话的 CSRF 校验值。
- 单条消息最多 2000 个字符，前端渲染前进行 HTML 转义。
- 输入区提供扩展常用表情库，包含“嘘”🤫、情绪、手势、爱心与行情相关表情；表情作为普通 Unicode 文字写入 `chat_message.body`，无需另建表。选择面板限制最大高度，表情增多时只在面板内部滚动，不挤压聊天区域。
- 支持点击选择或直接粘贴 JPG、PNG、GIF、WEBP 图片；单张最多 5MB，可以附带文字说明。
- 图片放在独立的 `chat_attachment` MySQL 表，不混入文字消息表，也不落入无需登录即可访问的静态目录；图片必须通过登录鉴权接口读取，且请求账号必须是消息发送者或接收者。
- 后端按文件头识别图片类型，不信任浏览器提交的扩展名或 MIME；SVG 与其他可能携带脚本的格式不开放。
- 打开的会话每 1 秒轻量增量读取新消息，联系人与未读状态每 3 秒刷新；两者都不整体刷新聊天页面。
- 联系人轮询结果没有变化时不重建联系人 DOM，避免列表闪动和滚动位置复位。
- 联系人支持按真实账号名或私人备注搜索；离线账号显示最近在线时间。
- 点击联系人头像可以设置最长 24 个字符的私人备注；备注只改变当前账号看到的联系人名称，不修改对方真实账号名，也不影响其他账号。清空后恢复显示真实账号名。
- 联系人备注写入独立的 `chat_contact_remark` 表并使用现有 AES-256-GCM 聊天密钥加密；它属于长期联系人设置，不随 7 天消息清理任务删除。
- 初次进入读取最近 100 条，继续向上按 100 条分页读取历史，且任何历史页都不能越过当前账号自己的清空游标。
- Enter 发送，Shift + Enter 换行；窄屏时联系人列表移到会话上方。
- 输入区显示字数和发送状态；用户向上阅读历史时，新消息不会强制把页面拉回底部。
- 左侧入口固定在主索引最底部，对外名称使用较低调的“协作记录”；功能内部仍保持一对一消息的安全边界。
- `user_account.chat_nav_hidden` 保存每个账号自己的入口隐藏偏好，不使用浏览器临时缓存，也不会影响其他账号。
- “运行规则”向全部账号展示当前账号的隐藏状态，只有管理员可以修改；入口隐藏后仍可从该规则卡片打开协作记录，避免失去访问路径。
- 页面标题下不展示一对一留言功能说明，左侧未读提示使用入口双跳动画，不显示 `NEW` 或具体未读数量；动画周期由 3.2 秒缩短为 1.6 秒，进入页面后仍可查看联系人自己的未读数。
- 协作消息使用独立于行情报警的声音开关；两个开关都以绿灯/灰灯勾选项显示，可以同时开启、分别开启或全部关闭。当前联系人会话处于前台且浏览器拥有焦点时，新消息直接显示但不播放协作声音；其他联系人、其他页面或后台窗口仍正常提醒。
- 自己发送的消息不再显示“已读/未读”文字：灰色空心圆表示未读，青蓝色勾圈表示已读；悬停勾圈显示该条消息的已读时间。消息发送时间始终在气泡下方显示，使用 UTC+8，不因回执改成图标而隐藏。
- 点击任意聊天气泡会出现轻量操作菜单：引用、复制、置顶/取消置顶、删除、撤回。引用关系写入共享消息；置顶和个人删除写入当前账号自己的消息偏好。
- “删除”先显示自定义确认框。收到的消息只能删除自己这一侧；自己发送的消息可勾选“同时为对方撤回”，不勾选时仍只影响自己。
- “撤回”仅允许消息发送者操作并需要再次确认。撤回后立即清空加密正文、删除图片附件、取消双方对该消息的置顶；双方原气泡改为无气泡的“你/对方撤回了一条消息”提示。
- 一个会话同时只保留一条个人置顶消息，置顶摘要固定显示在会话顶部。
- 引用可以指向文字或图片消息，并显示原文字或图片缩略图；点击引用后使用 `around_id` 读取原消息附近的历史并自动定位。原消息超过 7 天或被个人删除时显示不可用，原消息被撤回时显示“原消息已撤回”。
- 打开会话后的增量读取除新消息 ID 外，还携带撤回时间游标；因此对方撤回较早消息时，不需要整体刷新也能在约 1 秒内把原气泡替换为撤回提示。

## 7 天滚动留存

1. `chat_message` 与对应 `chat_attachment` 统一只保留最近 7 天。
2. 后台每 6 小时执行一次物理清理，清理结果写入 `automation_status.chat_retention_cleanup`，运行规则页展示固定的 7 天政策。
3. “清空我的记录”仍是个人可见游标，不立即删除对方副本；但消息超过 7 天后会对双方永久删除。
4. 图片与所属消息同生共灭；MySQL 热备份会同时包含文字和图片，不会产生只恢复消息、却丢失图片文件的残缺状态。

## 已验证场景

- 甲发送一条消息后，甲乙双方均能读取。
- 甲清空自己的记录后，甲读取为 0 条，乙仍能读取原来的 1 条。
- 101 条可见历史按“最近 100 条 + 更早 1 条”正确分页，并且更早读取不会穿过清空游标。
- 图片消息写入 MySQL 元数据并由会话双方读取；未登录请求被拒绝。
- 第 8 天的消息和附件会一并清除，第 6 天消息仍保留。
- 以上双方隔离、历史分页、账号级入口隐藏、低调未读标识、图片权限、滚动留存、并发去重、UTC+8 时间、逐条已读时间、账号封禁、私人联系人备注、引用跳转、个人删除、双方撤回与个人置顶场景均已加入自动化回归测试。

## 2026-08-04：图标回执与舒缓协作提示音

- `chat_message.read_at` 保存接收页面首次读到该条消息的 UTC 时间，界面统一转换为 UTC+8；新消息记录到秒。
- 旧消息原来只有会话已读游标，没有逐条时间。升级时使用对应 `chat_view_state.updated_at` 做一次兼容回填；这是可取得的最近似历史时间，之后不再覆盖。
- 实时轮询只把刚从未读变为已读的图标更新时间，不会用后续会话的最后阅读时间覆盖更早消息的准确回执。
- 协作提示音不再复用 1.5 秒急促行情报警声，改为约半秒的双音柔和提示；行情报警声音保持原样。

## 2026-08-03：账号私有联系人备注

- 联系人备注不是全局昵称，也不是管理员替账号改名；它只属于设置备注的当前账号。
- 联系人列表的头像作为备注编辑入口，备注保存后同步用于联系人列表、搜索和当前会话标题；存在备注时仍在次级信息里保留真实账号名，避免认错人。
- 备注值在 MySQL 中使用与聊天正文相同的应用层密钥加密，数据库仍会保留账号关系和更新时间等必要元数据。
- 清空备注会删除对应关系行并恢复真实账号名；消息、已读游标和个人清空游标均不受影响。

## 后续可扩展

- 若图片量增长或部署多台应用服务器，再把图片二进制迁移至带私有读权限的对象存储；接口与消息表结构可以保持不变。
- 普通文件暂未开放；需要先确定允许格式、单文件上限和病毒扫描方案，不能直接沿用图片白名单。
- 当前撤回未设置时间限制；若以后需要限制为发送后若干分钟，应只调整服务端撤回授权规则，不能依赖前端隐藏按钮。
- 如需管理员公告，应单独建立广播会话或公告表，不能伪装成普通私聊。

## 2026-08-03：发送延迟与重复气泡修正

- 线上核对结果：最近 24 小时没有同一发送方、接收方和时间重复入库的记录；“2 条短暂显示成 4 条、随后恢复 2 条”属于前端重复渲染，不是 MySQL 重复写入。
- 根因：发送成功后的主动读取与 3 秒轮询可能使用同一个旧游标并发请求，两个响应会把同一批消息重复追加到 DOM；之后完整读取又按数据库事实重建，因此重复气泡会自行消失。
- 修正：同一会话、模式和游标的并发请求复用同一个 Promise；所有响应先按消息 ID 去重，追加前再检查该 ID 是否已经渲染。
- 修正：发送接口成功返回后直接渲染服务器返回的消息，不再阻塞等待“消息重读 + 联系人重读”；联系人刷新改为后台执行。
- 修正：增加发送中的前端互斥锁，防止 Enter 与按钮操作在一次请求尚未结束时重复提交。
- 性能口径：打开会话时消息增量读取周期为 1 秒，联系人列表保持 3 秒；慢请求尚未结束时不会再发出相同游标的重复请求。

## 2026-08-03：UTC+8 与接收延迟复核

- 云服务器系统时区为 UTC；聊天表统一保存 UTC 的无时区时间，接口展示时统一转换成 UTC+8，避免云端与本地部署显示不同。
- 实测一组对话：发送接口与 MySQL 写入均在请求当秒完成；接收账号处于正常前台轮询时，最近一条消息写入与读取同秒完成。
- 同一组中另有 4 条消息在写入后约 123、126、141、165 秒才被接收账号读取。访问日志显示延迟段不是 Nginx 限流、接口缓存或 MySQL 阻塞，而是接收浏览器没有及时读取对应会话；重新进入页面后才批量读取。
- 页面从后台恢复、窗口重新聚焦、浏览器前进后退恢复页面或网络重新上线时，立即执行一次联系人和当前会话同步，不等待定时器。
- 服务端只记录不含正文的投递诊断：消息 ID、发送账号 ID、接收账号 ID和“写入到首次交给接收页面”的毫秒延迟，用于后续精确排查；不会记录密码、密钥或消息正文。

## 2026-08-03：短暂断线与发送状态核对

- 云端曾使用`--max-requests 500`回收唯一的Gunicorn worker；聊天高频增量读取会快速触发回收，在交接空窗内产生`Failed to fetch`。该请求次数回收已取消，PM2的内存上限继续兜底。
- 联系人与消息读取遇到短暂网络中断时最多自动重试两次，并在恢复后继续使用原游标增量读取，不清空现有会话内容。
- 发送请求发生连接中断时不能直接自动重发，因为消息可能已经写入MySQL、只是响应在途中断开；前端保留输入，自动补读会话核对结果，并显示中文状态，不再弹出原始英文网络错误。

## 2026-08-03：MySQL聊天内容加密

- 采用服务器端应用层加密，满足换电脑后只需登录账号即可继续读取；它不是端到端加密。
- 文字与图片分别使用AES-256-GCM和不同用途标识，随机数每条独立生成；数据库保留发送者、接收者、时间、图片类型和大小等必要元数据。
- 原始图片文件名不再保存，新图片统一保存为按可信MIME生成的通用名称，减少MySQL元数据泄露。
- `chat_message.encryption_version`与`chat_attachment.encryption_version`记录加密版本；启动迁移只处理版本0的旧数据，完成后置为版本1，重复启动不会再次加密。
- 密钥保存在项目外的`.chat_encryption.key`私密文件中并被Git忽略；数据库备份脚本将其作为独立恢复材料备份，SQL文件本身不携带密钥。
- 密钥丢失后任何管理员都无法恢复聊天密文；密钥与数据库同时泄露时保护失效，因此两者必须分开保存。

## 2026-08-03：收件提示与已读回执

- 报警声音不再只依赖联系人未读总数。当前会话的增量消息和联系人未读消息统一按数据库消息 ID 去重触发；当正在前台查看该联系人时不响，其他联系人或非前台场景仍提醒，联系人轮询不会对同一条消息重复发声；顶部协作声音开关仍然生效。
- 左侧“协作记录”取消醒目的 `NEW` 字样。首次载入已有未读或页面离开后收到新消息时，入口执行“两次轻跳、长暂停、继续循环”的低调动画；进入协作记录后立即停止，旧未读不会在离开页面后重新触发同一轮动画。
- `chat_view_state.last_read_message_id`同时承担接收方阅读游标。消息接口返回对方已经读到的最大消息 ID，发送方页面据此逐条显示“未读/已读”；状态只表示对方页面已经读取到该消息，不表示对方一定完成理解或处理。
- 已读状态通过现有 1 秒增量读取更新，不额外增加轮询线程或数据库表；消息正文、联系人和输入框字号统一小幅收紧。

## 2026-08-03：声音通道拆分

- 顶部声音控制拆分为“报警声音”和“协作声音”两个本机浏览器级开关，分别保存在 `arbi-alarm-sound` 与 `arbi-chat-sound`，互不覆盖。
- 绿灯表示对应通道已勾选开启，灰灯表示关闭；首次升级没有独立协作设置时，协作声音沿用升级前的报警声音状态，之后独立保存。
- 行情报警只读取报警声音开关，协作消息只读取协作声音开关；“测试声音”用于确认浏览器音频权限与设备音量，不改变两个开关的状态。

## 2026-08-05：离开当前会话后的协作声音补漏

- 已确认现象：联系人仍保持选中时，切到日报等其他功能页后，新消息会触发左侧入口动画，但部分浏览器没有播放协作提示音。
- 前台静音必须同时满足四个条件：当前激活区域就是“协作记录”、消息来自当前联系人、页面可见、浏览器拥有焦点；只保留联系人选中状态不能构成静音理由。
- 浏览器可能在刷新或重新登录后阻止没有经过用户交互的新音频上下文。页面会在首次点击或键盘操作时静默激活声音通道，不产生可听提示；之后离开协作页收到消息即可正常播放。
- 消息 ID 去重规则保持不变：同一条消息只提醒一次；入口跳动与声音共享同一新消息事实，但分别按页面状态和声音开关决定是否展示、播放。
- 发布时同步更新前端脚本版本标记，避免浏览器继续使用修正前的声音判定缓存。

## 2026-08-05：输入框与发送按钮对齐

- 表情、图片工具栏独占输入区上层，不再参与发送按钮的纵向定位。
- 文本输入框与发送按钮组成独立同排容器，按钮上下边缘跟随输入框拉伸对齐；图片预览出现时只在这一排上方展开，不会再次推偏按钮。
- 窄屏仍保留固定宽度的发送按钮，输入框使用剩余宽度，避免按钮溢出或挤压工具栏。

## 2026-08-07：iPhone 会话布局

- 手机端进入协作记录时先展示协作者列表，不自动打开第一位联系人；点选联系人后才切换到单会话视图，并可通过顶部返回按钮回到列表。
- 会话容器使用浏览器 `visualViewport` 的实时高度，软键盘展开或收起时同步调整消息区，输入框保持 `16px` 以上以避免 iOS Safari 自动缩放。
- 输入栏、表情面板和底部间距纳入 iPhone 安全区；桌面端双栏聊天布局和原有 1 秒消息增量读取、3 秒联系人读取规则保持不变。
- 当前仍是网页聊天。前台和重新唤醒后的补读继续有效，但网页退到后台或被 iOS 挂起时不能承诺实时收件；原生后台通知需要后续单独接入 Web Push 或 APNs。

## 2026-08-07：主屏模式声音授权与竖屏会话

- iPhone Safari 添加到主屏幕后可能形成独立的本地声音设置，且应用每次从后台恢复时 Web Audio 都可能重新进入挂起状态。协作页在声音关闭或本次前台尚未解锁时显示“开启声音”状态条；用户轻触后立即播放一次协作提示音作为授权和设备音量确认。
- 声音上下文不再只凭历史 `signalAudioPrimed` 标记判断可用，而是同时检查当前 `AudioContext.state`。新消息到达时若 iOS 拒绝自动恢复，记录一条待播放提示；用户下一次触摸页面并成功解锁音频后补播一次，不重复每条旧消息。
- 手机停留在协作者列表时，即使内部仍记得上次联系人，也不能误判为“正在前台查看该会话”而静音；只有单会话画面真实打开且消息来自当前联系人时，才沿用既有前台静音规则。
- 竖屏协作页隐藏全局行情标题、账号指标和悬浮 TIPS，仅保留安全区应用栏、协作声音状态及聊天主体。联系人列表和会话使用整个 `visualViewport`；会话采用纵向弹性布局，消息区占满剩余空间，发送栏固定在安全区上方并随软键盘高度收缩。
- 以上修正只覆盖前台网页声音。iOS 将主屏网页挂起后，JavaScript 轮询和声音都不会运行；后台系统通知仍需后续配置 Manifest、Service Worker、Web Push 订阅与服务端推送链路。
