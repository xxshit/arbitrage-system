# 聊天模块设计

记录时间：2026-08-01（2026-08-03 增加图片与 30 天留存）

## 目标

在 ArbiScope 登录账号之间提供一对一聊天，并满足“任意一方清空自己的聊天记录，不影响对方”的要求。聊天数据独立分表，不能与账号、行情、报警或盯盘表混用。

## 数据表

| 表名 | 作用 |
| --- | --- |
| `chat_message` | 保存发送者、接收者、消息正文和发送时间。消息是双方共享的原始事实。 |
| `chat_attachment` | 保存图片消息的所属消息、原文件名、可信 MIME 类型、大小、图片二进制和创建时间。 |
| `chat_view_state` | 保存每个账号针对每个联系人的可见游标、已读游标。清空只更新当前账号自己的游标。 |

## 独立清空语义

1. 甲和乙之间的原始消息仍保存在 `chat_message`。
2. 甲点击“清空我的记录”后，只把甲对应乙的 `cleared_through_id` 更新到当前最后一条消息。
3. 甲再次打开会话时，只读取该游标之后的新消息。
4. 乙的 `chat_view_state` 不发生改变，因此乙仍能看到原历史。
5. 清空后双方发送的新消息对甲、乙都正常显示。

这不是物理删除，也不是端到端加密。拥有数据库管理权限的人仍可维护数据库；网页普通账号只能读取自己参与的会话。

## 接口与前端

- 联系人接口返回其他有效账号、最近消息、在线提示和未读数。
- 消息接口只能读取当前账号与目标账号之间的双向消息。
- 发送和清空操作必须携带当前登录会话的 CSRF 校验值。
- 单条消息最多 2000 个字符，前端渲染前进行 HTML 转义。
- 输入区提供常用表情；表情作为普通 Unicode 文字写入 `chat_message.body`，无需另建表。
- 支持点击选择或直接粘贴 JPG、PNG、GIF、WEBP 图片；单张最多 5MB，可以附带文字说明。
- 图片放在独立的 `chat_attachment` MySQL 表，不混入文字消息表，也不落入无需登录即可访问的静态目录；图片必须通过登录鉴权接口读取，且请求账号必须是消息发送者或接收者。
- 后端按文件头识别图片类型，不信任浏览器提交的扩展名或 MIME；SVG 与其他可能携带脚本的格式不开放。
- 打开的会话每 1 秒轻量增量读取新消息，联系人与未读状态每 3 秒刷新；两者都不整体刷新聊天页面。
- 联系人轮询结果没有变化时不重建联系人 DOM，避免列表闪动和滚动位置复位。
- 联系人支持按账号名搜索；离线账号显示最近在线时间。
- 初次进入读取最近 100 条，继续向上按 100 条分页读取历史，且任何历史页都不能越过当前账号自己的清空游标。
- Enter 发送，Shift + Enter 换行；窄屏时联系人列表移到会话上方。
- 输入区显示字数和发送状态；用户向上阅读历史时，新消息不会强制把页面拉回底部。
- 左侧入口固定在主索引最底部，对外名称使用较低调的“协作记录”；功能内部仍保持一对一消息的安全边界。
- `user_account.chat_nav_hidden` 保存每个账号自己的入口隐藏偏好，不使用浏览器临时缓存，也不会影响其他账号。
- “运行规则”向全部账号展示当前账号的隐藏状态，只有管理员可以修改；入口隐藏后仍可从该规则卡片打开协作记录，避免失去访问路径。
- 页面标题下不展示一对一留言功能说明，左侧未读状态统一显示 `NEW`，不暴露具体未读数量；进入页面后仍可查看联系人自己的未读数。
- 联系人未读总数相较上一轮增加时复用全局报警声音播放一次；顶部处于静音时不播放，首屏已有旧未读不会因刷新页面反复响铃。

## 30 天滚动留存

1. `chat_message` 与对应 `chat_attachment` 统一只保留最近 30 天。
2. 后台每 6 小时执行一次物理清理，清理结果写入 `automation_status.chat_retention_cleanup`，运行规则页展示固定的 30 天政策。
3. “清空我的记录”仍是个人可见游标，不立即删除对方副本；但消息达到 30 天后会对双方永久删除。
4. 图片与所属消息同生共灭；MySQL 热备份会同时包含文字和图片，不会产生只恢复消息、却丢失图片文件的残缺状态。

## 已验证场景

- 甲发送一条消息后，甲乙双方均能读取。
- 甲清空自己的记录后，甲读取为 0 条，乙仍能读取原来的 1 条。
- 101 条可见历史按“最近 100 条 + 更早 1 条”正确分页，并且更早读取不会穿过清空游标。
- 图片消息写入 MySQL 元数据并由会话双方读取；未登录请求被拒绝。
- 第 31 天的消息和附件会一并清除，第 29 天消息仍保留。
- 以上双方隔离、历史分页、账号级入口隐藏、低调未读标识、图片权限、滚动留存和并发去重场景已加入自动化回归测试；当前完整测试共 25 项通过。

## 后续可扩展

- 若图片量增长或部署多台应用服务器，再把图片二进制迁移至带私有读权限的对象存储；接口与消息表结构可以保持不变。
- 普通文件暂未开放；需要先确定允许格式、单文件上限和病毒扫描方案，不能直接沿用图片白名单。
- 如需真正撤回，应设计“双方撤回”事件并明确时间限制，不能复用个人清空。
- 如需管理员公告，应单独建立广播会话或公告表，不能伪装成普通私聊。

## 2026-08-03：发送延迟与重复气泡修正

- 线上核对结果：最近 24 小时没有同一发送方、接收方和时间重复入库的记录；“2 条短暂显示成 4 条、随后恢复 2 条”属于前端重复渲染，不是 MySQL 重复写入。
- 根因：发送成功后的主动读取与 3 秒轮询可能使用同一个旧游标并发请求，两个响应会把同一批消息重复追加到 DOM；之后完整读取又按数据库事实重建，因此重复气泡会自行消失。
- 修正：同一会话、模式和游标的并发请求复用同一个 Promise；所有响应先按消息 ID 去重，追加前再检查该 ID 是否已经渲染。
- 修正：发送接口成功返回后直接渲染服务器返回的消息，不再阻塞等待“消息重读 + 联系人重读”；联系人刷新改为后台执行。
- 修正：增加发送中的前端互斥锁，防止 Enter 与按钮操作在一次请求尚未结束时重复提交。
- 性能口径：打开会话时消息增量读取周期为 1 秒，联系人列表保持 3 秒；慢请求尚未结束时不会再发出相同游标的重复请求。
